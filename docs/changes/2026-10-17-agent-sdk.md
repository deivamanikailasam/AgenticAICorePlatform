# agent-sdk and agentctl

## What changed
- New package `libs/agent-sdk` (`agent_sdk`), the stable surface for teams:
  - `@tool(...)` makes a `Tool` from an async function;
  - re-exports `PatternBuilder` and plan types, `Score`, `Observation`, `Task`, `Evaluator`,
    `ToolSpec`, `SideEffect`, `DataClass` and `RunContext`.
- New command line `agentctl`:
  - `validate`: checks the specs.
  - `run`: one run through the in-process run API, with the production assembly and in-process
    policy rules; or `--api URL` for a deployed run API, using `AGENT_API_TOKEN`.
  - `eval`: the golden tasks, with a saved report, failing below `--min-success`.
  - `promote` and `deploy-config`: through `ReleaseRepo`.
- `--provider none` is the default for agents without model nodes. An agent that calls a model
  in such a run gets an error saying how to give it one, not an invented answer.
- `agent_api.eval_runner` gains `gateway_provider()`, moved from `scripts/eval_app.py`, and a
  `root` argument to `evaluate()`, so a project's report names its own commit.

## Why
Step 39: an SDK for custom tools, patterns and evaluators, and `agentctl validate / run / eval /
promote`.

## How to check it
`uv run pytest libs/agent-sdk`: a project with an SDK tool validates, runs (`HELLO, ADA`),
evaluates 1/1 with provider `none`, promotes to staging, and passes `deploy-config --check`. A
failing task fails the eval; an unknown agent and a skipped staging are usage errors.

## Risks and follow-ups
The in-process run uses the policy rules that mirror OPA (parity-tested since Step 10). Deployed
runs use OPA itself.
