# Backups and a measured disaster-recovery drill for the agent database

## What changed
- `governance/dr.yaml`: the recovery objectives for the agent database (owner policy). It holds
  runs and events, checkpoints, memory, registry, approvals, usage, releases and the audit trail.
  - Targets: lose at most 300 s of writes (RPO), verified within 1800 s (RTO).
  - Backup method: base backup plus continuous WAL archiving (`archive_timeout` 60 s), kept off
    the database host.
- `just dr-drill` (`scripts/dr_drill.py`) runs the drill on a throw-away Postgres with the
  stand-in's image (pinned):
  - archives WAL, provisions and migrates the agent database, takes a base backup;
  - writes through the platform's own stores for 90 s: encrypted checkpoints, runs with events,
    pgvector memories, hash-chained audit events;
  - destroys the container and its data volume, then restores base backup plus archive to the end;
  - verifies the audit chain and every recovered item against what was written, plus memory
    search;
  - measures the recovery point and time, and records the result in `evals/results/dr/`.
- New `dr-drill` workflow: weekly, and on changes to the drill, the policy or migrations.
- Runbook `docs/runbooks/dr-restore.md`: how to restore for real and what to verify before
  reopening.

## Why
Step 38 Done-when: a DR drill restores state within the stated RPO/RTO. The targets are now
written down, and the drill checks them against real writes.

## How to check it
`just dr-drill`. This container's run (`evals/results/dr/agent-database-20261017T002403Z.json`):
- 340 writes acknowledged in 90 s; 116 of them, made after the last archived WAL segment, were
  lost.
- Measured RPO 32.3 s (target 300); measured RTO 5.0 s (target 1800).
- Audit chain intact over 56 rows; 56 runs, 56 checkpoints and 56 memories recovered and equal to
  what was written; 0 problems.

`uv run pytest libs/agent-governance/tests/test_dr.py` checks that the newest recorded drill
passed against the stated targets.

## Risks and follow-ups
- The drill uses a local volume where production uses object storage. The measured RTO is for a
  small database on one host; a real restore takes longer with size. Re-measure on the real
  environment (VERIFY-ON-MAC: Project 0's Postgres backups, in Kubernetes the operator's
  continuous archiving).
- The recovery point depends on `archive_timeout`: up to a minute of writes is at risk. Streaming
  replication to a standby narrows it; that belongs to Project 0's Postgres.
- Qdrant, when it is the memory store, needs its own snapshots; pgvector, the default, is covered
  here.
