# Three ways to route a request: LLM, embedding classifier, rules

**Step:** 15 · **Commit:** feat(agent-runtime): add LLM, embedding and rules routers · **Date:** 2026-10-15

## What changed
- `router.llm` (the default): the model picks a route with structured output that only allows
  the declared routes, optionally helped by a one-line description per route. A reply outside
  them is refused. The request is passed as data, not instructions.
- `router.embedding`: a classifier with no chat model. Labelled examples per route and the
  request are turned into vectors (`embedder` slot); the route whose closest examples are most
  similar wins. Example vectors are computed once per router and reused.
- `router.rules`: ordered patterns per route, first match wins; otherwise a default route with
  confidence 0.
- A router node chooses with `config.router` (or `components.router` for the whole spec), takes
  `examples` / `examples_file` for the embedding router and `rules` / `default` for rules, and can
  send unsure decisions (`min_confidence`) to a `fallback` route such as a human.
- Every routing result records the route, its confidence and the reason.

## Why
The spec asks for an LLM router with an embedding classifier or rules as alternatives. An LLM
understands open-ended wording but costs a model call per request; an embedding classifier is
cheaper and steadier once it has good examples; rules are free and fully predictable when the
vocabulary is fixed.

## How to check it
`uv run pytest libs/agent-runtime/tests/test_routing.py libs/agent-compiler/tests/test_routing_specs.py`
— all three routers pass the router contract, and each works from `agent.yaml` on both runtimes.

## Risks and follow-ups
How accurate each router is depends on the model and the examples; the next commits add a
labelled set and a harness to measure it. The tests use an offline hashing embedder, which only
proves the plumbing.
