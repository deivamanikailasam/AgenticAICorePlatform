# Memory through the Mem0 open-source library

**Step:** 20 · **Commit:** feat(agent-memory): Mem0 memory store · **Date:** 2026-10-15

## What changed
- **`memory_store.mem0`** uses the Mem0 open-source library (2.2.1), not Mem0's cloud service.
  - Items are stored and searched through Mem0's hybrid semantic and keyword search, on
    pgvector in the `agent` database.
  - The tenant is Mem0's `user_id`. Scope, subject, kind, key, version and expiry are metadata,
    filtered in the database.
- Three Mem0 behaviours are off or replaced on purpose:
  - **Fact extraction is off.** Mem0 would rewrite approved content with a model after the
    write policy ran, which reopens the poisoning path (ASI06).
  - **Embeddings come from the platform's `embedder` slot**, not Mem0's own provider client.
  - **Telemetry is disabled, and Mem0's change history stays in memory**, so no side file
    keeps personal data after an erasure.
- New dependencies: `mem0ai`, `psycopg-pool`. To satisfy Mem0, the lock resolves protobuf to
  6.33.6 (it was 7.36.2).

## Why
The spec lists Mem0 as an alternative for long-term memory. It suits teams already using Mem0's
API and its keyword-plus-vector search.

## How to check it
`uv run pytest -m integration libs/agent-memory/tests/test_mem0_integration.py` runs the store
contract, plus a check that stored content is exactly what the policy approved.

## Risks and follow-ups
- Mem0 embeds the text it stores, so content is not encrypted by the application. Rely on
  database encryption at rest, or choose pgvector or Qdrant when encrypted content is required.
- Replacing Mem0's embedding model uses its `embedding_model` attribute. A test pins this
  against mem0ai 2.2.1.
