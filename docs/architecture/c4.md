# C4 views

Three zoom levels: who uses the platform (context), what runs (containers), and what is inside
the run API (components). The deployment view shows how the containers sit in a cluster.

## 1. Context

```mermaid
flowchart LR
  user["Business user<br/>(starts runs, reads results)"]
  approver["Approver<br/>(approves irreversible actions)"]
  operator["Operator<br/>(releases, incidents, privacy)"]
  team["Another team<br/>(own agent project, Step 39)"]
  ext["Other agents and MCP clients<br/>(A2A, MCP)"]
  subgraph A["Project A: Agentic AI Core Platform"]
    core["Runs agents from agent.yaml<br/>under policy, approvals, budgets and audit"]
  end
  subgraph P0["Project 0: RAG Platform Foundation (reused, never forked)"]

  end

  user & approver & operator --> core
  team -->|"agent-sdk, template, pinned base"| core
  ext <-->|"signed Agent Cards, MCP"| core
  core --> p0
  core -->|"tools, after policy and approval"| apps
```

## 2. Containers

```mermaid
flowchart TB
  subgraph clients["Callers"]
    ui["Browser page / application"]
    mcpc["MCP client"]
    a2ac["A2A agent"]
  end
  subgraph pa["Project A (namespace agent-platform-<env>)"]
    api["agent-api<br/>run API: runs, threads, approvals, releases, AG-UI SSE/WS"]
    worker["agent-worker<br/>Temporal worker for durable agents"]
    mcpg["mcp-gateway<br/>platform tools, rag-core, allowlisted MCP servers"]
    a2ag["a2a-gateway<br/>signed Agent Cards, JSON-RPC, REST, gRPC"]
    sbx["sandbox-runner<br/>gVisor / Firecracker / Kata<br/>(a host process locally; its own nodes in production)"]
    temporal["Temporal"]
  end
  subgraph p0["Project 0"]
    llm["LiteLLM gateway"]
    pg["Postgres + pgvector<br/>runs, checkpoints, memory, audit, registry"]
    vk["Valkey<br/>idempotency, rate limits, release state"]
    s3["SeaweedFS S3<br/>artefacts, backups"]
    kc["Keycloak"]
    opa["OPA"]
    bao["OpenBao"]
    otel["OTel Collector"]
    rag["rag-core"]
  end
  ui -->|"bearer token"| api
  mcpc --> mcpg
  a2ac --> a2ag
  a2ag -->|"as the caller"| api
  api --> mcpg
  api --> temporal --> worker
  worker --> mcpg
  api & worker --> llm
  api & worker --> pg & vk & s3
  api & mcpg & a2ag --> kc & opa
  api & worker & mcpg --> bao
  api & worker & mcpg & a2ag --> otel
  mcpg --> rag
  api & worker -.->|"sandbox_python tool"| sbx
```

- Every container verifies Keycloak tokens itself. Nothing trusts the network.
- Every tool call is decided by OPA (or Cerbos or OpenFGA, the documented alternatives) before
  it runs.
- Secrets come only from OpenBao, as short leases.
- Locally, every port binds to 127.0.0.1. In a cluster, a default-deny NetworkPolicy allows
  only the arrows above.

## 4. Deployment

```mermaid
flowchart LR
  git["Git: deploy/ (base, overlays, releases, specs)"]
  argo["Argo CD"]
  subgraph cluster["Kubernetes"]
    subgraph ns["agent-platform-<env>"]
      d1["agent-api ×3 (prod)"]
      d2["mcp-gateway ×3"]
      d3["a2a-gateway ×3"]
      d4["agent-worker (KEDA on the task queue)"]
    end
    subgraph p0ns["rag-platform (Project 0)"]
      p0svc["shared services"]
    end
  end
  reg["GHCR: signed images, pinned by digest"]
  git --> argo --> ns
  reg --> ns
  ns --> p0svc
```

- **Changes:** every change goes through a pull request. `just promote` writes it; the promotion
  rules and eval gates check it; prod needs its named approver.
- **Images:** images are pinned by digest. The images workflow builds, signs and scans them.
- **Replicas:** dev, staging and prod differ only in replicas, resources and which agent
  versions serve.
- **Evidence:** deploy-e2e builds the same overlays on kind and checks them on every push
  ([results](../results.md)).
